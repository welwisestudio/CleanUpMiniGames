# Проверка качества

## Четыре разных вида доказательств

| Проверка | Что доказывает | Чего не доказывает |
|---|---|---|
| Unit / контракты | Правила наград, миграции, очередь SDK | Удобство мыши и красоту |
| UI fixtures | Композицию заданного состояния | Что игрок может реально до него дойти |
| E2E ввод | Прохождение через мышь/касание | Полный контракт реальной площадки |
| Platform / ручная | Поведение в YouTube и ощущение игры | Автоматическое покрытие всех комбинаций |

Playwright может получать координаты через dev-hook, затем выполнять реальные жесты. Нельзя назвать таким прохождением прямое изменение прогресса. В production dev-hook отсутствует; для проверки используйте обычный интерфейс и отдельный тестовый SDK на уровне окружения.

## Матрица

Для экранов: boot/error/retry, menu, settings, gameplay, hint, pause, result, reward, store, bonus, paywall и вложенные окна — проверяются применимые состояния. Для каждой механики: начало, частичное выполнение, ошибка, подсказка, завершение, пропуск, restart, смена уровня.

Размеры-ориентиры: 360×640, 390×844, 844×390, 768×1024, 876×876, 1440×900, 1920×1080. Дополнительно 320×240 и ultrawide как стресс-проверки. DPR 1/2 и дробный масштаб. Проверяй ориентацию во время drag, открытой модалки, полёта награды и смены стадии.

## Обязательные сценарии перед релизом

1. Настоящее прохождение уровня каждого семейства и полного короткого маршрута menu → игра → result → Next → menu.
2. Неверный ввод, touch cancel, быстрые повторные клики, потеря/возврат платформенной активности.
3. Повторный claim, x3, покупка при нехватке валюты, реклама true/false/reject и ответ после смены контекста.
4. Новое/старое/повреждённое сохранение, неизвестная версия, ошибка load, ошибка save, повтор и перезагрузка.
5. Смена порядка уровней без потери доступа; Next через обычный/VIP/бонус/последний уровень.
6. Начальная загрузка меню, недостающий ресурс, retry и отсутствие второй одновременной загрузки.
7. Production при строгом CSP, без inline-кода и без запрещённых платформой API, включая код движка.
8. Сеть: все игровые ресурсы локальны, внешние запросы соответствуют разрешённому профилю площадки.
9. ZIP: имена, состав, размер и совпадение с проверенным dist.
10. Ручной запуск в настоящем окружении YouTube и официальный Test Suite.

## Визуальная проверка

Сохраняй скриншоты с именем экрана, уровня, стадии, viewport и DPR. Составляй контактные листы, затем открывай подозрительные кадры отдельно. Проверяй фактические границы текста, пересечения с иконками, положение внутри кнопок, aspect ratio и читаемость. Анимации смотри в видео или в нескольких промежуточных кадрах.

Pixel-проверки полезны для локального стирания, неизменного дальнего участка, непрерывности переходов и выхода слоя за маску. Geometry checks не способны доказать привлекательность графики. Замерять надо не только финал, но и момент, на который пожаловался пользователь.

Для вырезанных ассетов проверь цепочку master → Higgsfield Background Remover → cutout PNG → runtime. Проверяй фактическую alpha, сохранность деталей, отсутствие каймы и шахматки, совпадение anchors и состояний после crop/resize. Сохраняй превью на светлом, тёмном и игровом фоне; отдельно проверяй runtime после сжатия. Статус completed у сервиса не означает PASS визуальной проверки.

## Отчёт и регрессии

В `project/VALIDATION.md`: билд/коммит, дата, команды, реальные результаты, пути артефактов, ручные проверки и ограничения. Старый PASS без повторного запуска обозначай историческим. Если тест падает, сначала проверь, не устарело ли ожидание после согласованной смены правил; не меняй assertion лишь для зелёного результата.

Не нужно писать тест, повторяющий каждую строку кода. Автоматизируй риски: потерю прогресса, повторные награды, неработающий ввод, платформенные ограничения и повторявшиеся дефекты. После изменений повторяй затронутые проверки и короткий общий маршрут.
