# YouTube Playables: инструкция для Phaser / JavaScript

Основа подробных сценариев — локальные документы, код и исправления ASMR. Официальные API и требования дополнительно проверены 2 октября 2026 года. Перед публикацией повторить сверку: платформа может измениться.

В новом процессе эта инструкция применяется на финальном этапе интеграции — после готового контента и принятого баланса. До этого игра использует dev-адаптер общего платформенного интерфейса. Порядок запуска ниже относится к финальной YouTube-сборке, а не к началу разработки игры.

## Источники внутри папки

- [Technical Information — исходный текст](source/technical-information.txt).
- [Исходная Unity-инструкция](source/unity-integration-original.md): сохранена без изменений для полноты, это справочный материал, не рабочая инструкция для Phaser.

Не переносить C#, `.jslib`, `PlayerPrefs`, Unity WebGL loader и `Time.timeScale` в JavaScript-игру. Переносится смысл требований: порядок старта, облако, звук, пауза и реклама. Для новой реализации использовать контракт [SDK-CONTRACT.md](SDK-CONTRACT.md).

## Краткая сверка официального API

SDK загружается до игрового кода. `firstFrameReady()` предшествует `gameReady()`. `loadData()` возвращает строку; `saveData(string)` — Promise. Rewarded возвращает boolean, а interstitial — `Promise<void>` без гарантии фактического показа. `getLanguage()` асинхронен. `sendScore({value})` принимает целое значение выбранной метрики. [Официальный SDK reference](https://developers.google.com/youtube/gaming/playables/reference/sdk).

Облако, управление звуком и pause/resume должны следовать правилам площадки. Для автоматической паузы внутри YouTube используется SDK, а не браузерный Page Visibility API. [Integration requirements](https://developers.google.com/youtube/gaming/playables/certification/requirements_integration).

Ниже — инженерные сценарии проекта и правила шаблона, а не обещание сертификации.

## 1. Старт и CSP

Платформенный index сначала подключает `https://www.youtube.com/game_api/v1`, затем внешний bootstrap, затем игру. После появления первого загрузочного кадра bootstrap уведомляет о first frame. Интерактивное меню появляется только после чтения прогресса и загрузки необходимых ресурсов; затем game ready.

Не держи вызов first frame во встроенном script: в ASMR его блокировала CSP. Внешний файл решает конкретный случай inline-запрета, но всё равно нужно проверить реальную политику площадки и способы подключения скриптов. Динамические скрипты/nonce требуют отдельной проверки.

Проверяй `typeof ytgame !== 'undefined'` и `ytgame.IN_PLAYABLES_ENV`. Глобальная lexical-переменная SDK не обязана быть свойством `window.ytgame`; тест должен воспроизвести этот вариант.

Не показывай ошибку облака при любой ошибке приложения. Раздели: SDK load, чтение/парсинг прогресса, загрузка ассетов, запуск движка. Отказ необязательного шрифта не означает повреждение сохранения.

## 2. Прогресс и запись

Порядок: чтение строки → parse → проверка версии и структуры → миграция → разрешение записи → создание приложения. Сохраняй после значимых изменений и при host pause; последнее окно перед закрытием может быть коротким.

Политика пустых значений в ASMR: пустая/пробельная строка, сериализованные `{}` и `null` означают отсутствие прогресса. Это решение игры. `undefined` в успешном ответе не следует молча принимать как пустой save: контракт ждёт строку. Reject/timeout, повреждённый JSON и неизвестная версия блокируют запись и дают Retry.

Миграции сохраняют заработанное: валюту, уровни, инвентарь и награды. Не вызывай «fresh save» для неизвестной будущей версии. Удалённый из нового контента ID требует явной политики, а не молчаливого обнуления.

Очередь записей последовательная; новые снимки могут заменять ещё не отправленные промежуточные. После ошибки старый снимок не должен перезаписать более новый. Dirty/error статус виден игроку, retry выполняется без параллельных гонок. Размер строки проверяется до SDK; в исходном проекте использовался консервативный порог меньше 3 МиБ с оценкой UTF-16 `length*2`.

В приложенной Unity-инструкции есть отдельная рекомендация считать UTF-8, тогда как описание SDK говорит о корректной UTF-16 строке. Это различие не следует скрывать. Для нового адаптера сверить действующий способ измерения и тест площадки; до этого держать большой запас и контролировать обе оценки (UTF-16 и UTF-8), не приближаясь к границе. Не сохранять изображения, аудио и логи внутри прогресса.

Для YouTube запрещён браузерный fallback прогресса: localStorage, sessionStorage и IndexedDB не заменяют облако. Тестировать нужно и с полностью недоступными browser storages. Dev-адаптер хранит тестовый прогресс отдельно; это не поведение релиза.

## 3. Пауза и звук

Адаптер получает начальный `isAudioEnabled()` и подписывается на изменения. Игра хранит независимые причины блокировки. Host pause останавливает игровой цикл, физику, timers, tweens, ввод, подсказки, музыку и эффекты. Host resume снимает только host pause: открытая пользователем пауза остаётся открытой.

Автоматическая приостановка не обязана показывать окно PAUSE. В ASMR пользователь отдельно потребовал, чтобы окно открывал только он сам.

Phaser 3.90 по умолчанию регистрирует обработчики visibility/focus. Присваивание `game.onHidden=()=>{}` не удаляет сами регистрации. В ASMR Vite-transform удаляет VisibilityHandler в ESM-сборке до обработки зависимостей. Его проверка требует ровно одно совпадение и останавливает сборку при изменении структуры движка.

Для нового проекта оформи это как платформенный профиль, зафиксируй версию Phaser, проверь dev и dist на запрещённые обращения и на фактическое отсутствие слушателей. Не редактируй node_modules вручную. Для другой площадки используй её lifecycle без наследования ограничений YouTube по умолчанию.

## 4. Rewarded

Каждое место показа имеет стабильный ID типа награды, например `game-hint`, `game-result-x3`, `game-unlock-level-id`. Не включай данные пользователя. Внутренний receipt операции и `rewardId` SDK — разные идентификаторы.

`true` даёт право применить награду, `false` — нет. Reject, unavailable, отсутствие SDK и host pause не равны просмотру. Во время запроса блокируй второй запрос и конкурирующую навигацию. Если ответ пришёл при host pause, дождись допустимого возобновления и проверь контекст операции.

Не добавляй interstitial сразу после rewarded, который запускает уровень. Mock-успех допускается только в отдельно выбранном dev-адаптере. В текущем ASMR есть локальный fallback при отсутствии SDK; шаблон сознательно заменяет его более явной архитектурой.

## 5. Interstitial

В ASMR запрошены естественные переходы: Play, выбор уровня, Next, Retry/Restart/Again, возврат в меню, вход/выход бонуса. Не вызывай рекламу при каждом техническом render окна или на первом появлении меню.

30 секунд — правило этого проекта, не универсальное утверждение о требованиях YouTube. Публичный API, проверенный при подготовке документа, не предоставляет доказательства impression. Поэтому «сбрасывать таймер только после реально показанной рекламы» невозможно гарантировать этим сигналом.

Принятый в ASMR компромисс: 30 секунд после успешно завершённого запроса; reject не сбрасывает таймер. Называй поле `lastInterstitialRequestCompleted`. Не угадывай показ по продолжительности или событиям pause/resume. Если продукт требует точного учёта показов, нужна поддержка такого сигнала площадкой и изменение адаптера.

## 6. Score, язык и диагностика

В ASMR score — число уникальных уровней с заработанными звёздами, максимум 58; повторы не увеличивают его. Для новой игры выбрать одну согласованную метрику. Новое значение отправлять после соответствующего сохранения, повторную отправку дедуплицировать и обрабатывать ошибку.

Язык получать через асинхронный API платформы; не хранить locale как постоянное предпочтение в облачном прогрессе YouTube. Наличие вызова locale не означает, что игра переведена: ASMR остался англоязычным. Health warning/error — диагностика, не продуктовая аналитика.

## 7. Проверка релиза

Сначала unit/контрактные тесты с управляемым SDK. Затем собранный production под реалистичной CSP: lexical SDK, ошибки load/retry, запрет browser storages, пустые и старые saves, пауза, mute, rewarded, score. Проверяй также код движка и отсутствие dev-hook.

После этого загрузи тот же ZIP в Playables Developer Portal и пройди официальный SDK Test Suite; проверь реальный аккаунт, облачное продолжение, доступность рекламы и телефон/ПК. Локальный успех не заменяет этот шаг — именно после него в Chat3 обнаружились недостающие условия тестового окружения.

Монетизация и доступ к её возможностям проверяются в портале. См. [YouTube Playables monetization](https://developers.google.com/youtube/gaming/playables/reference/monetization) и [страницу сертификации](https://developers.google.com/youtube/gaming/playables/certification/requirements). Состояние аккаунта нельзя вывести из локального кода.
